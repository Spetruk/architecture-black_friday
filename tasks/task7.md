# Architecture Design Record: Шардирование MongoDB для онлайн-магазина «Мобильный мир»

## Название задачи
Проектирование схем коллекций и стратегии шардирования для масштабирования онлайн-магазина

## Функциональные требования

### Use Cases

| № | Действующие лица | Use Case | Описание |
|---|-----------------|----------|----------|
| UC1 | Клиент, Система управления заказами, Система управления складом | Создание заказа | 1. Клиент добавляет товары в корзину<br>2. Клиент оформляет заказ<br>3. Система создаёт заказ и списывает остатки товаров<br>4. Заказ сохраняется со статусом "pending" |
| UC2 | Клиент, Система поиска | Поиск товаров по категории | 1. Клиент выбирает категорию товаров<br>2. Система выполняет поиск с фильтрацией по цене<br>3. Возвращается список товаров с актуальными остатками |
| UC3 | Гость/Клиент, Система управления корзинами | Работа с корзиной | 1. Пользователь добавляет товар в корзину<br>2. Система создаёт/обновляет корзину<br>3. При авторизации гостевая корзина сливается с пользовательской |
| UC4 | Клиент, Система заказов | Просмотр истории заказов | 1. Клиент запрашивает свои заказы<br>2. Система возвращает список заказов с сортировкой по дате |
| UC5 | Система управления складом | Обновление остатков | 1. При поступлении товара обновляются остатки по геозонам<br>2. При покупке остатки уменьшаются атомарно |

## Нефункциональные требования

| № | Требование | Описание |
|---|------------|----------|
| NFR1 | Производительность | Время отклика на запросы поиска товаров < 100мс для 95 перцентиля |
| NFR2 | Масштабируемость | Поддержка роста до 10 млн товаров и 100 млн заказов |
| NFR3 | Доступность | 99.9% SLA для критичных операций (заказы, корзины) |
| NFR4 | Консистентность | Строгая консистентность для операций с остатками товаров |
| NFR5 | Географическое распределение | Оптимизация для работы в разных геозонах |
| NFR6 | Производительность записи | Поддержка 10000 операций записи в секунду |

## Решение

### Архитектурный подход

Для обеспечения горизонтального масштабирования и высокой производительности выбрана стратегия шардирования MongoDB с учётом специфики каждой коллекции.

### Схемы коллекций

#### 1. Коллекция `products`

```javascript
{
  "_id": ObjectId("..."),
  "product_id": "PROD-12345",  // String, уникальный идентификатор
  "name": "Смартфон Samsung Galaxy S24",  // String
  "category": "electronics",  // String, индексированное поле
  "price": 89990,  // Number
  "stock": {  // Object с остатками по геозонам
    "moscow": 150,      // Number
    "spb": 75,         // Number
    "ekb": 30,         // Number
    "kaliningrad": 20  // Number
  },
  "attributes": {  // Object с дополнительными атрибутами
    "color": ["black", "white", "purple"],  // Array
    "memory": ["256GB", "512GB", "1TB"]     // Array
  },
  "created_at": ISODate("2024-01-15T10:00:00Z"),  // Date
  "updated_at": ISODate("2024-01-20T15:30:00Z")   // Date
}
```

**Стратегия шардирования: Составной ключ**
```javascript
sh.shardCollection("shop.products", { category: 1, _id: "hashed" })
```

**Обоснование:**
- Распределение по категориям обеспечивает локальность данных для запросов фильтрации
- Хэширование _id гарантирует равномерное распределение внутри категории
- Поддерживает эффективные targeted queries по категориям

#### 2. Коллекция `orders`

```javascript
{
  "_id": ObjectId("..."),
  "order_id": "ORD-2024-001234",  // String, уникальный идентификатор
  "customer_id": "CUST-98765",     // String, ключевое поле для шардирования
  "created_at": ISODate("2024-01-20T14:30:00Z"),  // Date
  "items": [  // Array of Objects
    {
      "product_id": "PROD-12345",
      "name": "Смартфон Samsung Galaxy S24",
      "quantity": 1,     // Number
      "price": 89990,    // Number
      "category": "electronics"
    }
  ],
  "status": "processing",  // String: "pending"|"processing"|"shipped"|"delivered"|"cancelled"
  "total_amount": 89990,   // Number
  "geo_zone": "moscow",    // String
  "shipping_address": {    // Object
    "city": "Москва",
    "street": "ул. Тверская, д. 1",
    "postal_code": "125009"
  }
}
```

**Стратегия шардирования: Составной ключ**
```javascript
sh.shardCollection("shop.orders", { customer_id: 1, created_at: 1 })
```

**Обоснование:**
- Группировка заказов клиента на одном шарде для эффективных запросов истории
- Монотонный рост по времени предотвращает hotspots
- Оптимально для запросов вида "все заказы клиента за период"

#### 3. Коллекция `carts`

```javascript
{
  "_id": ObjectId("..."),
  "user_id": "CUST-98765",           // String, null для гостей
  "session_id": "sess-abc123def456",  // String, основной ключ шардирования
  "items": [  // Array of Objects
    {
      "product_id": "PROD-12345",
      "quantity": 2,              // Number
      "added_at": ISODate("2024-01-20T13:00:00Z")  // Date
    }
  ],
  "status": "active",  // String: "active"|"ordered"|"abandoned"
  "created_at": ISODate("2024-01-20T13:00:00Z"),  // Date
  "updated_at": ISODate("2024-01-20T13:15:00Z"),  // Date
  "expires_at": ISODate("2024-02-19T13:00:00Z")   // Date, TTL
}
```

**Стратегия шардирования: Хэшированный ключ**
```javascript
sh.shardCollection("shop.carts", { session_id: "hashed" })
```

**Обоснование:**
- Равномерное распределение активных сессий по всем шардам
- Избегание hotspots при пиковых нагрузках
- Простота масштабирования при росте трафика

### Конфигурация кластера

```javascript
// Инициализация шардированного кластера
sh.enableSharding("shop")

// Создание индексов перед шардированием
db.products.createIndex({ category: 1, price: 1 })
db.products.createIndex({ name: "text" })
db.products.createIndex({ "stock.moscow": 1 })

db.orders.createIndex({ customer_id: 1, created_at: -1 })
db.orders.createIndex({ status: 1, created_at: -1 })
db.orders.createIndex({ geo_zone: 1 })

db.carts.createIndex({ user_id: 1, status: 1 })
db.carts.createIndex({ session_id: 1, status: 1 })
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })

// Настройка репликации для каждого шарда
rs.initiate({
  _id: "shard1",
  members: [
    { _id: 0, host: "shard1-primary:27017", priority: 2 },
    { _id: 1, host: "shard1-secondary1:27017", priority: 1 },
    { _id: 2, host: "shard1-secondary2:27017", priority: 0 }
  ]
})
```

### Мониторинг и метрики

#### Ключевые метрики:
1. **Балансировка данных**
   ```javascript
   db.products.getShardDistribution()
   sh.status()
   ```

2. **Производительность запросов**
   ```javascript
   db.products.find({ category: "electronics" }).explain("executionStats")
   ```

### Ограничения:
1. **Размер шард-ключа** не должен превышать 512 байт
2. **Невозможность изменения** шард-ключа после создания коллекции

### Риски:
1. **Операционный риск:** Сбой config-серверов может сделать кластер read-only
   - *Митигация:* Развернуть config replica set минимум из 3 узлов - пока не сделано

### Меры по снижению рисков:
1. **Резервное копирование:** Настройка continuous backup
2. **Мониторинг:** Интеграция с Prometheus/Grafana для отслеживания метрик
3. **Документация:** Подробные runbooks для типовых сценариев восстановления

## Заключение

Предложенная архитектура шардирования обеспечивает:
- **Горизонтальную масштабируемость** до миллионов товаров и заказов
- **Высокую производительность** за счёт оптимальных шард-ключей
- **Отказоустойчивость** через репликацию и географическое распределение
- **Гибкость** для будущего роста и изменения требований

Выбранные стратегии шардирования учитывают специфику каждой коллекции и паттерны доступа к данным, обеспечивая оптимальный баланс между производительностью, масштабируемостью и операционной сложностью.
