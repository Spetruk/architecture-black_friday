
# Architecture Design Record: Миграция на Cassandra

## Название задачи
Миграция критически важных данных интернет-магазина с MongoDB на Apache Cassandra для обеспечения масштабируемости, отказоустойчивости и минимальных задержек при экстремальной нагрузке.

---

## Часть 10.1 — Анализ критически важных данных

### Выбранные сущности:

| Сущность               | Причина критичности |
|------------------------|---------------------|
| **orders**             | Высокая частота записей, критичность целостности и доступности |
| **carts**              | Высокая частота обновлений, важность актуальности |
| **user_sessions**      | Высокая скорость доступа, важность геораспределения |
| **order_history**      | Требуется быстрый доступ по пользователю, объём большой |
| **products**           | Основной каталог, но частота обновлений невысока |

**Исключено:** данные о товарах (`products`) не требуют высокой скорости записи и не являются горячими — могут оставаться в другой БД (например, MongoDB или Redis в виде кеша).

## Часть 10.2 — Концептуальная модель данных и ключи

### 1. Таблица: `orders`

```cql
CREATE TABLE orders_by_customer (
    customer_id text,
    order_id uuid,
    created_at timestamp,
    status text,
    total_amount decimal,
    items list<frozen<item>>,
    PRIMARY KEY ((customer_id), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

- **Partition key**: `customer_id` — равномерное распределение по пользователям
- **Clustering key**: `created_at`, `order_id` — поддержка сортировки и уникальности

🟢 Используется для частых чтений "последние заказы клиента", масштабируется по пользователям

---

### 2. Таблица: `carts`

```cql
CREATE TABLE carts (
    session_id uuid,
    user_id text,
    updated_at timestamp,
    items map<text, int>,
    status text,
    PRIMARY KEY ((session_id))
);
```

- **Partition key**: `session_id` — равномерное распределение по активным сессиям
- Без кластеризации: сессия одна на строку, обновляется целиком

🟢 Часто обновляется, требует высокой доступности и низкой задержки

---

### 3. Таблица: `user_sessions`

```cql
CREATE TABLE user_sessions (
    user_id text,
    session_id uuid,
    device text,
    last_active timestamp,
    location text,
    PRIMARY KEY ((user_id), last_active)
) WITH CLUSTERING ORDER BY (last_active DESC);
```

- **Partition key**: `user_id` — группировка всех сессий пользователя
- **Clustering**: `last_active` — сортировка последних сессий

🟢 Часто используется для авторизации и аудита, доступ по пользователю

---

### 4. Таблица: `order_history`

```cql
CREATE TABLE order_history (
    order_id uuid,
    event_time timestamp,
    event_type text,
    event_details text,
    PRIMARY KEY ((order_id), event_time)
);
```

- **Partition key**: `order_id` — вся история заказа в одном разделе
- **Clustering**: `event_time` — упорядоченные события

🟢 Используется для отслеживания прогресса заказа, небольшое количество записей на заказ

---

## Партиционирование и горячие ключи

- Все ключи выбраны так, чтобы избежать **hot partitions**:
  - Нет прямого использования `status`, `geo_zone` или `category` как партиционирующего ключа
  - Используются UUID, user_id и session_id, которые имеют высокую кардинальность

## Часть 10.3 — Стратегии обеспечения целостности

### Обзор стратегий:

| Стратегия             | Назначение                                      |
|-----------------------|--------------------------------------------------|
| **Hinted Handoff**    | Временное хранение записи, если реплика недоступна |
| **Read Repair**       | Фоновая коррекция данных при чтении              |
| **Anti-Entropy Repair** | Периодическая полная синхронизация реплик        |

### Стратегии по сущностям:

| Сущность         | Стратегия                  | Обоснование |
|------------------|----------------------------|-------------|
| `orders`         | ✅ Read Repair + Anti-Entropy | Обеспечить корректность статусов заказов |
| `carts`          | ✅ Hinted Handoff           | Сессии часто обновляются, важна скорость |
| `user_sessions`  | ✅ Hinted Handoff + Read Repair | Быстрая запись, но точность важна для безопасности |
| `order_history`  | ✅ Anti-Entropy              | Допустима задержка синхронизации, важна полнота |

---

## Заключение

Переход на Cassandra оправдан для высоконагруженных и быстро обновляемых данных (заказы, корзины, сессии). Cassandra позволяет:

- 🔁 Надёжно масштабироваться горизонтально без решардинга
- 🧩 Обеспечить высокую доступность при сбоях узлов
- ⚖️ Равномерно распределить нагрузку по всем узлам

Была разработана схема с учётом hot keys, latency, доступности и консистентности, обеспечивая отказоустойчивую и масштабируемую архитектуру для пиковых нагрузок.
