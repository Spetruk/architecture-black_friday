
# Architecture Design Record: Настройка чтения с реплик и консистентность

## Название задачи  
Оптимизация операций чтения в MongoDB с использованием вторичных реплик для повышения производительности при сохранении консистентности данных.

## Контекст и проблема  
В онлайн-магазине «Мобильный мир» данные хранятся в коллекциях `products`, `orders` и `carts`. Для повышения масштабируемости и отказоустойчивости используются реплика-сеты. Для части операций чтения допустимо использовать вторичные реплики (`secondary`), но при этом важно сохранить корректность данных, особенно в сценариях, связанных с остатками товаров и оформлением заказов.

## Требования

### Функциональные

- Разгрузить primary-реплики за счёт безопасного использования secondary
- Сохранить строгую консистентность там, где это критично для бизнеса
- Обеспечить быструю доступность данных для пользователей (SLA < 100мс для чтения товаров)

### Нефункциональные

- Допустимая задержка репликации (replication lag): до 2 секунд для некритичных данных
- Обеспечение согласованности и предотвращение ошибок заказа на несуществующий товар

## Таблица: Стратегии чтения по коллекциям

| Коллекция | Операция чтения | Источник (Primary / Secondary) | Обоснование | Допустимая задержка |
|-----------|------------------|-------------------------------|-------------|----------------------|
| `products` | Каталог товаров (поиск, фильтры) | ✅ Secondary | Каталог может быть слегка устаревшим | ≤ 2 сек |
| `products` | Проверка остатка при добавлении в корзину | ❌ Только Primary | Критична точность остатков перед заказом | 0 сек |
| `products` | Админка: отчёты по складу | ✅ Secondary | Возможна задержка в статистике | ≤ 5 сек |
| `orders`   | История заказов пользователя | ✅ Secondary | Заказ сохраняется только после commit, можно читать с задержкой | ≤ 2 сек |
| `orders`   | Проверка статуса активного заказа | ❌ Только Primary | Нельзя показывать устаревший статус | 0 сек |
| `carts`    | Получение текущей корзины | ❌ Только Primary | Корзина часто обновляется, нужна актуальность | 0 сек |
| `carts`    | Аналитика по брошенным корзинам | ✅ Secondary | Используется для отчётов, не влияет на UX | ≤ 10 сек |

## Обоснование выбора

- **Products**: операции поиска могут использовать `secondary`, поскольку пользователь не ожидает идеальной точности, но остаток при заказе — всегда с primary.
- **Orders**: исторические данные стабильны, но текущий статус (например, «отгрузка») критичен.
- **Carts**: взаимодействие с корзиной происходит в реальном времени, консистентность — приоритет.

## Настройки MongoDB

```javascript
// Пример использования read preference на стороне клиента
db.products.find(...).readPref("secondaryPreferred")
db.orders.find({ user_id: "CUST-123" }).readPref("secondary")

// Для критичных операций:
db.products.find({ product_id: "P-001" }).readPref("primary")
```

## Альтернативы

### Использовать только primary

- ✅ Максимальная консистентность  
- ❌ Снижение производительности и увеличение нагрузки на primary

### Использовать secondary без ограничений

- ✅ Максимальная разгрузка primary  
- ❌ Риск устаревших данных → потери заказов/некорректный UX

## Риски и митигации

| Риск | Последствие | Митигация |
|------|-------------|-----------|
| Репликация отстаёт > 5 сек | Пользователь видит устаревший каталог | Мониторинг `replicationLag`, fallback на primary |
| Сбой secondary | Увеличение нагрузки на primary | Автоматическое переключение на primary-only чтение |

## Заключение

Принята сбалансированная стратегия:  
- **Каталог и история** — читаются с реплик,  
- **Ключевые операции (остатки, корзина, активные заказы)** — только с primary.

Это позволяет масштабировать систему, не жертвуя бизнес-логикой и пользовательским опытом.
